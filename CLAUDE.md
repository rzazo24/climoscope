# climoscope

App de clima en vanilla HTML/CSS/JS — sin frameworks, sin build tools, sin API key. Usa la API de [Open-Meteo](https://open-meteo.com/) para geocoding y pronóstico.

Este archivo ya no está en `.gitignore`: se puede versionar con el resto del repo.

## Estructura

```
index.html       estructura de la página, sin lógica
css/style.css     todos los estilos
js/app.js         toda la lógica: geocoding, fetch de clima, render, estado
sw.js             service worker (cachea el app shell, ver Convenciones)
manifest.json     manifest de la PWA
icons/            iconos de la PWA (192, 512, 512 maskable)
test/             tests automatizados (ver Testing)
package.json      solo existe para `npm test` — la app en sí sigue sin dependencias
```

No hay build step. `index.html` se sirve tal cual (rutas relativas a `css/` y `js/`).

## Cómo correr localmente

Necesita servirse por HTTP (no abrir con `file://`, falla por CORS):

```bash
python3 -m http.server 8000
```

## Testing

`npm test` (usa `node --test`, sin dependencias, Node 18+). Como `js/app.js` no exporta nada (sin módulos, a propósito, ver Convenciones), los tests no pueden importar funciones sueltas — en su lugar `test/dom-stub.js` monta un `document`/`window`/`localStorage`/`fetch` falsos (igual que hacía yo a mano en el sandbox durante la conversación para verificar cambios) y cada test `require()`ea `js/app.js` fresco contra ese entorno, comprobando qué queda en `mainPanel.innerHTML`/`localStorage`. Es un test de integración del script completo, no un test unitario de funciones aisladas — es la única forma posible dado que no hay exports.

Detalles importantes si se toca la suite:
- **Un escenario por archivo** (`test/*.test.js`): cada archivo de `node --test` corre con sus propios globals (verificado empíricamente, no asumido) — así que un `require()` fresco de `app.js` en cada archivo no arrastra estado de otros tests, sin necesidad de limpiar `require.cache` a mano entre archivos.
- `test/dom-stub.js` hace `delete require.cache[...]` de todas formas antes de cada `require()`, por si algún día se juntan varios escenarios en el mismo archivo.
- Node define `navigator` como global de solo lectura — no se puede hacer `global.navigator = {}` directo, hay que `Object.defineProperty` (si esto rompe en una versión nueva de Node, es la causa más probable).
- `global.setInterval` se sobrescribe a un no-op en el stub — si no, el `setInterval` de 30s (reloj) y el de 5min (`checkForAppUpdate`) dejarían el proceso de test colgado.
- **Descubrimiento de tests de Node**: `node --test` sin argumentos también intenta ejecutar como test cualquier `.js` dentro de `test/` aunque no termine en `.test.js` (así que recogía `dom-stub.js`/`fixtures.js`/`mock-fetch.js` como "tests" vacíos). Por eso `package.json` usa `node --test test/*.test.js` (glob del shell) en vez de `node --test` a secas — si se añade un test nuevo, que termine en `.test.js`.
- No se hacen peticiones de red reales: `test/fixtures.js` tiene respuestas de Open-Meteo/air-quality con la forma exacta que lee `app.js`, y `test/mock-fetch.js` las sirve según qué endpoint pida la URL (`v1/forecast`, `v1/air-quality`, `geocoding-api`, `nominatim`).

## Convenciones del código

- Todo en `js/app.js`, sin módulos ES ni bundlers — funciones globales simples.
- Código en inglés (identificadores, comentarios). UI en inglés por defecto la primera vez; el botón `#langToggle` cambia a español en caliente vía el diccionario `STRINGS` (en/es) y `WEATHER` (en/es por código de clima). **El idioma SÍ se persiste** entre recargas, bajo `climoscope:lang` (`loadLang()`/`saveLang()`) — esto cambió a petición del usuario; originalmente arrancaba siempre en inglés a propósito (ver historial), pero se revirtió para que se comporte como unidad/ciudad. Si se toca esto, no reintroducir el arranque forzado en inglés sin que el usuario lo pida explícitamente otra vez.
- Estado en variables globales de módulo (`unit`, `lang`, `lastData`, `favoriteCities`, etc.), no hay framework de estado.
- `favoriteCities` se persiste en `localStorage` bajo la key `climoscope:favorites` (sin límite de tamaño, deduplicadas por lat/lon). Se marca/desmarca con el botón `.fav-btn` (icono estrella) junto al nombre de la ciudad actual en `renderAll`; ese botón se recrea en cada render (está dentro del `innerHTML` de `mainPanel`), así que su listener se re-adjunta cada vez, no se cachea como el resto de refs del DOM.
- Menú de favoritos (`#favoritesBtn`/`#favoritesMenu`): antes era una fila de chips siempre visible debajo del buscador (`#favoritesSection`); a petición del usuario ahora es un botón-estrella en la propia fila de búsqueda (entre el input y `#geoBtn`) que despliega un dropdown. El dropdown reutiliza literalmente las clases `suggestions`/`suggestion-item` del autocompletado de ciudades (mismo `id="favoritesMenu"` pero `class="suggestions"` en el HTML) en vez de tener CSS propio — si se cambia el estilo de las sugerencias, esto también cambia. `favoritesBtn` lleva `.toggle-btn` (mismo estilo que geo/unidad/idioma) más `.active` (ámbar) cuando hay ≥1 favorito. Si la lista está vacía se muestra un `suggestion-item.empty` con `t('noFavorites')` en vez de ocultar el botón — el botón siempre está visible, solo cambia si tiene contenido útil o el mensaje vacío. `renderFavorites()` hay que llamarla también al cambiar de idioma (`langToggle`) porque el estado vacío tiene texto traducido — antes no hacía falta porque los chips solo mostraban nombres de ciudad, sin texto propio de la UI.
- Reordenar favoritos (`moveFavorite()`, botones `.reorder-btn` con `CHEVRON_UP_SVG`/`CHEVRON_DOWN_SVG`): a petición del usuario, botones subir/bajar en vez de arrastrar-y-soltar — se descartó drag-and-drop explícitamente porque la API nativa del navegador apenas funciona en iOS Safari, y esta app es muy mobile-first (ver el resto de fixes de iOS en este archivo). Cada `.suggestion-item` de favorito pasó de 2 a 2 hijos igualmente (para no romper el `justify-content:space-between` compartido con las sugerencias normales de ciudad): `.fav-item-info` (nombre+país, como antes) y `.fav-item-actions` (los dos botones). Los botones de reordenar hacen `e.stopPropagation()` en su click — si no, el click burbujea al listener del `.suggestion-item` padre y cargaría el clima de esa ciudad en vez de solo reordenar. El índice para `moveFavorite()` se calcula con `Array.from(favoritesMenu.children).indexOf(item)`, que coincide con el índice en `favoriteCities` porque el orden de renderizado es el mismo array — si se cambia el orden de renderizado (p. ej. alfabético) esto dejaría de ser cierto y habría que guardar el índice real en un `data-*` en su lugar. El primer favorito no puede subir ni el último bajar (`disabled`, con opacidad reducida vía CSS) en vez de que el botón haga un no-op silencioso.
- Abrir/cerrar el menú de favoritos SIEMPRE pasa por `setFavoritesMenuOpen(bool)` (toggle de `.open` en `#favoritesMenu` + `.visible` en `#menuBackdrop` a la vez) — no tocar `favoritesMenu.classList` directamente en ningún sitio nuevo, o el backdrop se desincroniza. Se cierra: al hacer click fuera (el listener de `document` ya cubre esto — el backdrop en sí no necesita su propio listener, un click ahí burbujea a `document` igual que cualquier otro), al escribir en el buscador, y al elegir un favorito.
- `#menuBackdrop`: overlay fijo de pantalla completa con `backdrop-filter: blur()`, pensado para el menú de favoritos (a petición del usuario, "que se desenfoque el fondo"). `z-index:9`, un punto por debajo de `.suggestions`/`#favoritesMenu` (`z-index:10`) — así el propio dropdown queda nítido encima del blur. `pointer-events` va de `none` a `auto` solo cuando está `.visible`, para que no bloquee clics cuando está invisible pero sí "absorba" el click de cierre sin que además dispare algún botón que hubiera debajo. Si en el futuro se quiere el mismo blur para `#suggestions` (autocompletado de ciudad), reutilizar este mismo elemento con `setFavoritesMenuOpen`-style helper, no crear un backdrop nuevo.
- Iconos de `.fav-btn`/`.share-btn`/`#geoBtn`: SVG inline (`STAR_SVG`/`SHARE_SVG` como constantes de string, el de geo directo en `index.html`), no emoji. Motivo: un emoji (🔗, etc.) tiene colores propios fijos que ignoran `color`/`currentColor`, así que el `:hover`→ámbar que tienen el resto de botones no le hacía nada — y además varía de aspecto según el emoji font del sistema operativo. Los SVG usan `fill="currentColor"` (estrella) o `stroke="currentColor"` (compartir, geo) para heredar el color del botón y reaccionar igual al hover/`.active` que el resto de la UI. Si se añade un icono nuevo a este grupo, seguir el mismo patrón (SVG + currentColor), no un emoji.
- No hay lista de "ciudades recientes": se probó y se quitó a petición del usuario (quedaba redundante con favoritos). Si se vuelve a pedir, no reintroducir el auto-guardado de cada ciudad vista — que sea explícito, como favoritos.
- Ciudad de arranque: se persiste bajo `climoscope:lastCity` (se guarda en cada `loadWeather` con éxito, incluida la de geolocalización). En el init se usa esa si existe; si no (primera visita), cae a Madrid hardcodeado.
- Compartir por URL: cada `loadWeather` con éxito llama a `updateUrlForCity()`, que hace `history.replaceState` con `?lat=&lon=&name=&country=` — así la barra de direcciones siempre es un enlace válido a la ciudad actual (sin ensuciar el historial de atrás/adelante, por eso `replaceState` y no `pushState`). En el init, `getSharedCityFromUrl()` tiene prioridad sobre `lastCity`/Madrid si la URL trae `lat`/`lon` válidos. Si la URL no trae `name` (alguien pega un enlace manual solo con coordenadas), se usa `reverseGeocode()` (el mismo de "mi ubicación") y si falla cae a `t('myLocation')`, igual que la geolocalización. El botón `.share-btn` (🔗, junto a la estrella) usa `navigator.share` si existe (móvil, hoja de compartir nativa) o si no, copia al portapapeles y enseña un ✓ 1.2s.
- Unidad °C/°F: se persiste bajo `climoscope:unit` (`loadUnit()` valida que sea `'F'` o si no cae a `'C'` por defecto). `unit` se inicializa desde `localStorage` al cargar el módulo, así que la primera renderización ya usa la unidad correcta sin esperar a que el usuario toque el botón — por eso `applyStaticText()` también fija `unitToggle.textContent` (antes solo lo hacía el handler del click).
- Geolocalización (`#geoBtn`, símbolo ⌖): usa `navigator.geolocation.getCurrentPosition` del navegador. El botón se oculta solo si `navigator.geolocation` no existe (Safari viejo, contexto no seguro, etc.); los errores de permiso/timeout se tratan todos igual, con un único mensaje genérico (`geoError`), igual que el resto de errores de la app.
- Reverse geocoding de "mi ubicación": Open-Meteo no lo ofrece, así que se usa `nominatim.openstreetmap.org/reverse` (OpenStreetMap, sin API key, CORS abierto). Es "best effort": `reverseGeocode()` atrapa cualquier fallo (red, 403, sin `name`/`address`) y devuelve `null`, y el handler del click cae de vuelta a `t('myLocation')`/"Mi ubicación" sin país — el mismo comportamiento que había antes de añadir Nominatim, así que un fallo aquí nunca rompe la función de geolocalización en sí.
- **Ojo con `Referer`**: Nominatim exige un `User-Agent` identificable o, si no se puede (caso típico de fetch desde el navegador, donde `Referer` es una cabecera prohibida que no se puede fijar por JS), un `Referer` válido — que un navegador real SÍ manda solo automáticamente en peticiones cross-origin. **No se puede probar este endpoint con `curl`/Node tal cual** (sin `-e`/Referer da 403); solo funciona de verdad desde un navegador real sirviendo la página por HTTP(S), no desde este sandbox. Si algún día deja de funcionar en producción, probar primero si Nominatim ha empezado a bloquear también peticiones con Referer de origen (no de ruta completa) antes de asumir que el código está mal.
- Atribución: al usar datos de OpenStreetMap, la política de Nominatim exige atribución visible — está en el footer (`footer` en `STRINGS`, menciona "OpenStreetMap" además de "Open-Meteo"). No quitarla si se toca ese texto.
- Cualquier texto que venga de la API (nombre de ciudad, país) se inserta con `escapeHtml()` antes de ir a `innerHTML` — no quitar eso.
- Las funciones `fetchSuggestions` y `loadWeather` usan un contador de request (`searchRequestId` / `weatherRequestId`) para descartar respuestas que ya no son las más recientes (evita condiciones de carrera si el usuario escribe rápido o cambia de ciudad rápido). Si se toca esa lógica, mantener el guard.
- Manejo de errores: siempre comprobar `res.ok` y el campo `data.error` que devuelve Open-Meteo antes de asumir que la respuesta es válida.
- Índice UV: viene del propio `hourly.uv_index` de la API principal (no existe en `current`), se lee el valor de la hora actual (`currentHourIdx`, ya calculado y reutilizado para el scroll de horas).
- Calidad del aire: viene de un endpoint aparte (`air-quality-api.open-meteo.com`, `current=european_aqi,us_aqi,pm10,pm2_5,carbon_monoxide,nitrogen_dioxide,sulphur_dioxide,ozone`), pedido en paralelo con `Promise.all` junto al forecast. Es una métrica "bonus": si falla (red, `data.error`, sin `current`), se traga el error con un try/catch propio y se muestra `—`, sin tirar abajo el resto del render. **`airQuality` guarda el objeto `current` completo** (no solo el número) precisamente para que el modal de detalle (ver más abajo) tenga los contaminantes disponibles — si se toca esto, `aqiInfo()` sigue esperando `airQuality.european_aqi`, no `airQuality` directo. El número se colorea según la categoría (`AQI_LEVELS`/`aqiInfo()`, umbrales del European AQI de Open-Meteo: 0-20 Good, 20-40 Fair, 40-60 Moderate, 60-80 Poor, 80-100 Very Poor, 100+ Extremely Poor) y lleva la categoría como `title` (tooltip). Solo 4 colores para 6 categorías (Good/Fair comparten verde, Very Poor/Extremely Poor comparten rojo) porque 6 tonos distintos no se distinguen bien a ese tamaño.
- Modales de detalle genéricos (`.detail-modal`/`.detail-modal-content`/`.detail-modal-header`/`.detail-modal-close`/`.detail-row`/`.detail-label`/`.detail-value`/`.detail-section-title`, más `.clickable-metric` para el número que abre cada uno): CSS compartido entre `#aqiModal` y `#precipModal` (y cualquier modal de detalle futuro) — originalmente eran clases `.aqi-*` específicas, se generalizaron al añadir precipitación para no duplicar el CSS del modal. Solo `.aqi-category` (la categoría coloreada tipo "Fair"/"Moderate") se quedó específica de AQI, porque precipitación no tiene ese concepto. **Si se añade un modal nuevo**: reutilizar estas clases genéricas + un par de funciones propias `setXxxModalOpen()`/`openXxxModal()` siguiendo el patrón de abajo, no crear CSS nuevo para el "chrome" del modal (fondo, cabecera, botón cerrar, filas).
- Modal de calidad del aire (`#aqiModal`, número clicable `.aqi-val.clickable-metric`): clic en el número abre categoría + AQI europeo + AQI de EE.UU. + los 6 contaminantes (PM2.5, PM10, NO₂, O₃, SO₂, CO, en µg/m³ — ver `fmtPollutant()`) + polen. El botón `.aqi-val` solo lleva el listener si `aqi` es no-nulo (si la API de calidad del aire falló, no tiene sentido abrir un modal vacío).
- Modal de precipitación (`#precipModal`, número clicable `.precip-val.clickable-metric`, `fmtMm()`): clic en la tarjeta "Precipitation" (total de HOY, `daily.precipitation_sum[0]`, redondeado a 1 decimal) abre el desglose: total, lluvia (`rain_sum`), chubascos (`showers_sum`), nieve (`snowfall_sum`, ojo que esta viene en **cm**, no mm, a diferencia de las demás), y horas con precipitación (`precipitation_hours`). A diferencia de polen, aquí NO se oculta nada condicionalmente — un `0` es un valor real y normal (día seco), no un "sin datos", así que siempre se muestran las 5 filas.
- Ambos modales (`#menuBackdrop` compartido, `refreshBackdrop()`): reutilizan el mismo desenfoque de fondo que el menú de favoritos en vez de crear uno propio — `refreshBackdrop()` centraliza la visibilidad del backdrop compartido (comprueba si favoritos, AQI o precipitación están abiertos) y hay que actualizarla ahí mismo si se añade un modal nuevo, o el backdrop se queda mal sincronizado. Cada modal (`.detail-modal`) es un wrapper de pantalla completa por encima del backdrop (`z-index:11` vs `9`) para poder centrar la tarjeta de contenido — por eso CADA UNO necesita su propio listener de click (`e.target === elModal`) para cerrarse al pulsar fuera de la tarjeta, ya que un click ahí nunca llega al backdrop (queda tapado).
- Polen (`alder_pollen`, `birch_pollen`, `grass_pollen`, `mugwort_pollen`, `olive_pollen`, `ragweed_pollen`, en `grains/m³` — ver `fmtGrains()`): Open-Meteo **solo lo da para el dominio CAMS europeo**; fuera de Europa los 6 campos vienen `null` (comprobado con Nueva York). Por eso la sección de polen en el modal es condicional: se comprueba `pollenFields.some(([, v]) => v != null)` antes de pintarla — si TODOS son `null` (fuera de Europa) no se muestra nada, no un montón de guiones. Ojo: un valor `0` (polen fuera de temporada, p. ej. abedul en septiembre) es un dato real, no "sin datos" — no confundir `0` con `null` aquí.
- Amanecer/atardecer y probabilidad de lluvia: `daily.sunrise`/`sunset` y `hourly.precipitation_probability` vienen como strings/números sin offset de timezone (ya vienen desplazados a la hora local por `timezone=auto`). Se leen con `new Date(...)` **sin** pasar `timeZone` explícito a `toLocaleTimeString`/`toLocaleDateString` — igual que el resto de horas/días. Solo `updateClock` pasa `timeZone` porque ese sí recalcula "ahora" en tiempo real. La probabilidad de lluvia por hora solo se pinta si es `> 0` (si no, queda en blanco) para no llenar el scroll de "0%".
- PWA: `sw.js` vive en la raíz (no en `js/`) a propósito, para que su scope por defecto sea `/` y pueda controlar `index.html`. Solo cachea el app shell (`index.html`, `css/style.css`, `js/app.js`, `manifest.json`, iconos); las peticiones a Open-Meteo/geocoding son cross-origin y el `fetch` handler las ignora explícitamente para que el clima nunca se sirva desde caché. Estrategia **network-first** (no cache-first): intenta red primero y solo cae a caché si falla (offline) — así los que ya tienen la PWA instalada ven el último deploy en la siguiente carga sin tener que hacer nada, sin depender de acordarse de subir `CACHE_NAME` en cada cambio. Si se añade/renombra un archivo del app shell, sí hay que actualizar `PRECACHE_URLS` en `sw.js` (para que el `install` inicial lo precachee).
- Banner de "nueva versión disponible" (`#updateBanner`): **NO** se detecta vía `controllerchange`/versión del service worker — probado y no funcionaba, porque `sw.js` es network-first y casi nunca cambia de bytes él mismo (los cambios normales son en `index.html`/`css/style.css`/`js/app.js`, que el SW sirve siempre frescos de red sin necesitar una versión nueva de `sw.js`). El mecanismo real es `checkForAppUpdate()`: compara el `ETag`/`Last-Modified` de `js/app.js` (fetch con `cache:'no-store'`) contra el que había al cargar la página; si cambió, se muestra el banner. Se comprueba al cargar, cada 5 minutos (`setInterval`) y al volver a la pestaña (`visibilitychange`). El listener de `controllerchange` se dejó como señal secundaria (por si `sw.js` cambia alguna vez), pero no es el mecanismo principal. El botón solo hace `location.reload()`.
- Número de versión en el footer (`footer .version`, en `index.html`): hardcodeado a mano (p. ej. `v1.2.0`), enlaza al `CHANGELOG.md` en GitHub. **No se calcula solo** — no hay build step que pueda derivarlo de un tag de git. Cada vez que se cree un tag nuevo y se actualice `CHANGELOG.md`, hay que actualizar también este número en `index.html` en el mismo commit, o se queda desincronizado silenciosamente.

## Despliegue

GitHub Pages, sirviendo desde la raíz de la rama `main` (Settings → Pages → Deploy from a branch → main → /root). No requiere `.nojekyll` ni build.

- Foto de fondo aleatoria (`#photoLayer`, `PHOTO_IDS` + `setRandomBackgroundPhoto()`): usa `picsum.photos/id/{id}/1600/900` — sin API key, a diferencia de Pexels que el usuario propuso primero y se descartó por eso (exponer una key en un repo público sin backend). Picsum no tiene filtro por tema/palabra clave, así que `PHOTO_IDS` es una lista curada a mano (revisada una por una para que no aparezcan personas, a petición del usuario) en vez de usar el endpoint random sin filtrar. Se elige una vez por carga de página (no en cada cambio de ciudad/clima), y también al volver de segundo plano (`visibilitychange`). Va en su propia capa (`position:fixed;z-index:-1`, DETRÁS de `.app` gracias al z-index negativo pero DELANTE del `background` propio de `body`), a `opacity:0.35` fijo — así el degradado de `setSky()` sigue tiñendo el tono por encima sin tapar del todo la foto. **Si se toca esto**: no meter la foto dentro del `background` shorthand de `body` junto a los gradientes existentes — se probó primero así y la foto quedaba invisible, porque esos gradientes son opacos y cubren toda la caja; por eso está en su propio elemento con su propia opacidad.
- Robot aleatorio en el masthead (`#robotAvatar`, `setRandomRobot()`): capricho friki pedido por el usuario, sin más función que decorativa. Usa `robohash.org/{seed}.png?set=set1` — `set1` fuerza el set de "robots" específicamente (RoboHash también tiene monstruos, cabezas y gatitos en otros sets). La seed es aleatoria en cada carga (`Math.random().toString(36)`), así que sale un robot distinto cada vez — a diferencia de la foto de fondo, este **no** se refresca al volver de segundo plano, solo en carga de página (no se pidió esa consistencia, se puede añadir si se pide). Sin API key, mismo criterio que Picsum. RoboHash a veces tarda o falla en responder (confirmado: un usuario no podía llegar a `robohash.org` en absoluto desde su red, y el propio sandbox tampoco — timeout de conexión — mientras Picsum/GitHub/Open-Meteo respondían normales, así que no es un problema puntual de una IP); mientras carga (o si falla del todo) `robotAvatar.style.visibility = 'hidden'` para no enseñar el icono de "imagen rota" (se veía como un "?"), pero sin quitar el elemento del layout — así el hueco (fondo/borde de `.robot-avatar`) sigue reservado y no hay salto de layout cuando por fin carga. Se usa `visibility`, no `display:none`, precisamente para conservar ese hueco. Además, si RoboHash tarda más de `ROBOT_TIMEOUT_MS` (4s) en cargar O si el `<img>` dispara `onerror`, se sustituye por `ROBOT_FALLBACK_SRC` — un robot mínimo dibujado a mano como SVG en un data URI (no se puede usar `currentColor` dentro de un `<img src>`, así que el color `--text-dim` va fijo en el propio SVG) — para que nunca quede el hueco vacío indefinidamente si el servicio está caído. `setRandomRobot()` usa una bandera `settled` + `clearTimeout` para que solo se aplique lo primero que ocurra (carga real vs timeout) y no se pisen entre sí; el `setTimeout` del timeout se `unref()`ea (con guarda `typeof timeoutId.unref === 'function'`, porque en el navegador `setTimeout` no devuelve un objeto con `.unref`) — sin eso, cada test que llama a `loadApp()` dejaba un timer real de 4s vivo y `npm test` pasó de ~5s a ~24s porque `node --test` esperaba a que el proceso de cada archivo de test drenara el event loop.

- Icono de niebla (`FOG_ICON`, códigos 45/48): SVG inline en vez de el emoji 🌫️, que en Apple/Noto se dibuja como un cuadrado gris de textura (parece una imagen rota). El resto de iconos del clima siguen siendo emoji; `WEATHER[code].icon` se inserta en `innerHTML`, así que admite SVG.
